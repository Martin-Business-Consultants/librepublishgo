Going live with Libre Publish

From an empty server to a live CMS on Hoster, with the old site's content brought in. One site per app; repeat for each site.

The one rule: every site keeps everything (database, uploads, secret key) in its own volume at /data. The repository's config/deploy.yml sets that up, and the CMS refuses to start without it, so a deploy can't wipe a site again.

Before you start

  • Hoster is connected to GitHub with access to Martin-Business-Consultants/librepublishgo.
  • The server is set up in Hoster.
  • The CMS's domain (e.g. cms.oldmillbrew.com) points at the server: a DNS A record to its IP.
  • You have the old site's backup (e.g. cms-backup-oldmill-….tar.gz), if you're moving one over.

Go live

  1. Create the app In Hoster: New app, from the GitHub repository Martin-Business-Consultants/librepublishgo, branch main.
    • Name it after the site, e.g. oldmill. The name becomes the site's volume: oldmill-data.
    • Every site needs a name of its own. Never reuse one.
  2. Add the domain Domains › Add domain: cms.oldmillbrew.com. Hoster takes care of HTTPS.
  3. Set the variables Under Variables:
    NameValue
    SITE_KEYoldmillRequired. The site's name. It ties the volume to this site.
    APP_URLhttps://cms.oldmillbrew.comOptional. The admin records it the first time you open it.
    Port 80, the /up health check, TRUST_PROXY and the volume come from the repository. Don't add them by hand.
  4. Deploy Press Deploy. When it's done, Logs shows libre publish is up, and Volumes lists oldmill-data at /data.
    If the log says the data directory isn't on a persistent volume, the volume didn't apply. Check that the app is deploying from main (the repository's config/deploy.yml) and deploy again. Nothing has been lost; the CMS stopped before writing anything.
  5. Open the admin Go to https://cms.oldmillbrew.com/cms/.
    • Moving a site over? Make a first admin on the setup screen (it's replaced in the next step), then carry on.
    • Starting fresh? The account you make on the setup screen is your admin. Skip step 6.
  6. Bring the old site in In the admin: Tools › Import.
    • Upload the backup, and read the report: files, forms, and the content changes it makes.
    • Type REPLACE and press Replace this site.
    • Sign in with an account from the old site.
    The import tidies the content as it comes in: textareas with HTML become Tiptap rich text, the image_url fields go, and alt text moves onto the images. There's no step after it.
  7. Turn on backups In Hoster, Backups: set a Backup schedule (nightly) for oldmill-data, then press Back up now once to see it work. You can also download a backup from the admin at any time: Tools › Backup.
  8. Connect the website
    • In the admin, Settings › Service tokens: create a token on the Production site role.
    • On the website's host, set CMS_BASE_URL=https://cms.oldmillbrew.com and CMS_API_TOKEN=<that token>.
    • In Settings › General: Public site URL https://oldmillbrew.com, and under Allowed origins, the website's address (one per line).
    • Rebuild the website. npx librepublish-astro sync updates its cms.lock.json if the CMS's schema changed.

Working on it with AI agents

On your own machine, with the same librepublish program:

librepublish login https://cms.oldmillbrew.com     # approve it in the admin
librepublish doctor                                # checks it all works
librepublish mcp setup                             # the line to add it to Claude Code, Codex, Cursor…

The agent then works on the site through its tools (pages, entries, media, settings…), as you and with your role. Every site is an MCP server at /mcp too. The repository's docs/agents.md has the details.

Live. Check Site health on the dashboard. Everything there should pass, including the CMS address.

Updating

  1. See what's new The dashboard says when a new version is out, with a link to its notes (releases).
  2. Back up Hoster Backups › Back up now (the button below also takes its own).
  3. Update Press Update now on the dashboard. It takes a backup into the site's own volume (/data/backups/), downloads the new version there (checked against the release's checksums), and restarts on it: a few seconds offline. The database updates itself on start. If the new version doesn't come up, the CMS goes back to the one before and the dashboard says so.

Each site updates on its own, from its own volume. Deploying a newer image from Hoster works too, and takes over from an update made with the button. To go back, deploy the previous version from Hoster. If a release's notes say it changed the database, restore the backup from /data/backups/ (Tools › Import) instead.

Several sites on one server

Each site gets its ownExample
App (and so volume)oldmill → oldmill-data, acme → acme-data
Domaincms.oldmillbrew.com, cms.acme.com
SITE_KEYoldmill, acme
Backup scheduleone per volume

The first start records SITE_KEY in the site's volume. A container with a different SITE_KEY refuses that volume, so two sites can't end up sharing one database by mistake. If one app has two environments on the same server (staging and production), give each its own service name in its settings, so each gets its own volume.

If something goes wrong

You seeWhat to do
Deploy fails: target failed to become healthyOpen Logs. The CMS prints one line saying why it stopped. The usual ones are below.
the data directory isn't on a persistent volumeDeploy from main (it has config/deploy.yml) and check Volumes. For a quick throwaway trial only: EPHEMERAL_DATA=1.
the data directory belongs to another siteTwo sites are pointed at one volume. Give each app its own name, or fix SITE_KEY.
Images point at localhostOpen the admin once as an Administrator, or set Settings › General › CMS address.
Forms say "Couldn't send"Add the website's address to Settings › General › Allowed origins.
Locked outHoster Shell: librepublish user password --email you@example.com --password -, then type the new password.
